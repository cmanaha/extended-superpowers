// THE APPROACH

Why I call it a flywheel

Each turn feeds the next. What one turn researches, verifies, and records, the next turn starts from — so the loop carries context forward instead of beginning cold.

Before any design, a planning session researches and an environment-research phase runs a dependency to see how it actually behaves, recording the findings in memory. Adversarial review at the spec, plan, and implementation gates turns findings into recorded corrections. The definition-of-done gate is enforced by tooling, so “done” is checked rather than asserted.

Those outputs — verified behaviour, recorded corrections, acceptance criteria, an enforced definition of done — are what the next turn starts from.

// THE PHASE I LEAN ON

Why the research phase

Documentation tells you what a library is meant to do. It rarely tells you how it behaves once its pieces combine, or how it fails. Over time I found that the gap between the docs and the real behaviour — the error modes and integration modes that only surface when you actually run things — is exactly where an agent quietly designs against a wrong assumption.

You don't feel it then. You feel it later: debugging, walking the code, hunting a failure the spec never accounted for. With a complex enough combination of libraries, an AI won't anticipate every error mode — and recovering from that downstream is slow and frustrating.

So before any spec or plan, I run small experiments against the real dependency — exercise it, provoke its failures, learn its error and integration modes — and fold the findings into the spec. It costs time up front; it saves a far worse loop later.

// SCALE IT TO THE PROBLEM

Not every phase, every time

These phases are optional. I dial them to how complex the problem is — the harder it is, the more time I spend on research and review; the more I already know going in, the less.

Complex problem → the full cycle

When I'm aiming a heavily-leveraged agentic run that will work for hours, I run everything: research, environment-research, adversarial review at every gate, acceptance tests, and the enforced definition of done. For that kind of autonomous work, the resilience is worth the cost.

Known, local change → the light path

When I know exactly which part of the architecture I'm touching, I drop most of it and keep superpowers' original loop plus the definition of done and telemetry. No point running an hours-long gauntlet on a small, well-understood change.

It trades tokens for resilience — by Anthropic's own data, multi-agent runs use on the order of 15× the tokens of a single chat. So grade the loop to the blast radius: heavy where a missed bug is expensive, light everywhere else.

// GET IT

Install

In Claude Code, on any machine. superpowers resolves automatically as a declared dependency.

/plugin marketplace add cmanaha/extended-superpowers
/plugin install extended-superpowers@cmanaha

Self-contained and environment-agnostic: it bundles its own review agents and reads from a generic memory store if one is present — never from anyone's personal setup. Restart Claude Code after installing.
